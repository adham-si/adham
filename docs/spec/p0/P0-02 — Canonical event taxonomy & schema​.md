<aside>
🧬

The canonical event log is Adham’s durable source of truth. Commands express intent; trusted application services enforce invariants and append immutable facts. UI state, model context, projections, and mutable agent objects are never authoritative.

</aside>

## Scope

This specification defines:

- Event identity and naming.
- Envelope fields.
- Stream and ordering rules.
- Correlation, causation, and actors.
- Payload schemas and compatibility.
- Sensitive-content separation.
- Integrity checks.
- Initial event taxonomy.
- Future event families reserved for the P0 runtime.
- Replay, corruption, and unknown-version behavior.

It does not define the complete SQLite table design or projection storage; that belongs to P0-03.

# 1. Command, event, and projection separation

## Command

A command is a request to perform work:

```
CreateWorkspace
CreateProject
CreateSession
SubmitMessage
```

Commands can be rejected. They are transport inputs and are not stored as canonical facts merely because they arrived.

## Event

An event is an immutable fact that has already been accepted:

```
workspace/created
project/created
session/created
user/message-submitted
```

Only trusted application services create events. The renderer, model, plugin, MCP server, or tool cannot select an event type or append directly.

## Projection

A projection is a rebuildable view of canonical events:

```
workspace list
project list
conversation
activity timeline
```

Projection rows may be replaced or rebuilt. Canonical events may not.

# 2. Naming and versioning convention

Use a stable lowercase event type with slash-separated domain and fact:

```
workspace/created
project/created
session/created
user/message-submitted
```

The version is a separate integer field:

```
event_type: "user/message-submitted"
event_version: 1
```

Do not encode the version into the event-type string. This keeps routing stable while allowing explicit decoder selection.

Rules:

- Event types describe facts in past tense.
- Names are never reused for different semantics.
- Renaming creates a new event type or an explicit migration.
- Additive optional fields may remain in the same version only when all consumers preserve the same meaning.
- A required-field change, type change, semantic change, or privacy change requires a new version.
- Persisted events are never rewritten just to match the newest schema.

Schema paths:

```
schemas/events/envelope/v1.json
schemas/events/workspace/created/v1.json
schemas/events/project/created/v1.json
schemas/events/session/created/v1.json
schemas/events/user/message-submitted/v1.json
schemas/events/registry.json
```

# 3. Canonical envelope

```rust
pub struct StoredEvent {
    pub global_position: GlobalPosition,
    pub event_id: EventId,
    pub event_type: EventType,
    pub event_version: EventVersion,

    pub stream_id: StreamId,
    pub stream_kind: StreamKind,
    pub stream_sequence: StreamSequence,

    pub scope: EventScope,
    pub actor: EventActor,

    pub request_id: RequestId,
    pub correlation_id: CorrelationId,
    pub causation_id: Option<EventId>,

    pub occurred_at: OffsetDateTime,
    pub recorded_at: OffsetDateTime,

    pub payload: Box<RawValue>,
    pub metadata: EventMetadata,

    pub previous_checksum: Option<EventChecksum>,
    pub checksum: EventChecksum,
}
```

## Field semantics

### `global_position`

A database-assigned monotonically increasing position across all events. It supports subscriptions and projection cursors. It is not the authority for order inside a stream.

### `event_id`

Globally unique UUIDv7 generated by the backend. It never changes across replay, export, or projection rebuild.

### `event_type` and `event_version`

Select the exact decoder and JSON schema.

### `stream_id`, `stream_kind`, and `stream_sequence`

Identify the aggregate stream and its authoritative order.

### `scope`

Carries immutable workspace/project/session relationships needed for isolation and audit.

### `actor`

Identifies who caused the fact: local human, system component, agent, tool, plugin, or migration.

### `request_id`

Connects the event to the idempotent command attempt.

### `correlation_id`

Connects all events and diagnostics belonging to one user-visible operation or later task.

### `causation_id`

Points to the event that directly caused this event. The first event produced by a command may omit it; later events in a workflow reference their direct cause.

### `occurred_at`

The backend-created domain timestamp in UTC.

### `recorded_at`

The storage timestamp assigned when committed. For local synchronous P0 commands it will normally be close to `occurred_at`, but the two meanings remain distinct.

### `payload`

The exact versioned event payload encoded as canonical UTF-8 JSON.

### `metadata`

Small, non-sensitive technical metadata. It is not a dumping ground for arbitrary context.

### Checksums

Provide corruption detection and per-stream chaining; they are not a substitute for authorization or encryption.

# 4. Typed identifiers

Raw strings and UUIDs do not cross the domain unchecked.

```rust
pub struct EventId(Uuid);
pub struct RequestId(Uuid);
pub struct CorrelationId(Uuid);
pub struct InstallationId(Uuid);
pub struct ActorId(Uuid);
pub struct WorkspaceId(Uuid);
pub struct ProjectId(Uuid);
pub struct SessionId(Uuid);
pub struct MessageId(Uuid);
pub struct ContentId(Uuid);
```

Use UUIDv7 for newly generated durable IDs when supported by the selected UUID crate version. Their time ordering helps diagnostics and indexes, but no authorization or event order may depend on UUID ordering.

IDs serialize as lowercase hyphenated UUID strings.

# 5. Stream model

Initial stream kinds:

```rust
pub enum StreamKind {
    Workspace,
    Project,
    Session,
}
```

Canonical stream IDs:

```
workspace:{WorkspaceId}
project:{ProjectId}
session:{SessionId}
```

Rules:

- Sequences begin at 1.
- Sequences are contiguous per stream.
- Append requires `expected_sequence`.
- A new stream expects sequence 0.
- The transaction fails on mismatch.
- No event becomes visible without its complete transaction.
- Cross-stream global order is observational; business invariants use aggregate relationships and explicit causation.

A command may append to more than one stream only when one database transaction can maintain all affected invariants. Avoid multi-stream writes when one owning aggregate and downstream projections are sufficient.

# 6. Event scope

```rust
pub struct EventScope {
    pub installation_id: InstallationId,
    pub workspace_id: Option<WorkspaceId>,
    pub project_id: Option<ProjectId>,
    pub session_id: Option<SessionId>,
}
```

Scope requirements:

| Stream kind | Workspace | Project | Session |
| --- | --- | --- | --- |
| Workspace | Required | Empty | Empty |
| Project | Required | Required | Empty |
| Session | Required | Required | Required |

Scope is copied into the envelope so security filtering does not require decoding arbitrary payloads.

On append, the application service validates the relationships against canonical state. A caller cannot broaden scope by supplying different IDs.

# 7. Actor model

```rust
pub enum ActorKind {
    LocalHuman,
    System,
    Agent,
    Tool,
    Plugin,
    Migration,
}

pub struct EventActor {
    pub actor_id: ActorId,
    pub kind: ActorKind,
}
```

P0-02 initially emits only:

- `LocalHuman` for accepted local user commands.
- `System` for initialization or repair events.
- `Migration` for explicit format migration facts if later needed.

Agent, tool, and plugin actors are reserved but cannot be used before their identity and permission contracts exist.

# 8. Sensitive-content separation

Canonical structural events must minimize personal and project content.

Do not store the full user message directly inside `user/message-submitted`. Store content through a separate content port in the same transaction and reference it from the immutable event:

```rust
pub struct MessageSubmittedV1 {
    pub message_id: MessageId,
    pub content_id: ContentId,
    pub content_kind: ContentKind,
    pub size_bytes: u64,
}
```

The content store owns:

- Message body.
- Content encoding and media type.
- Future encryption metadata.
- Deletion or cryptographic erasure.
- Content-specific integrity checks.

Benefits:

- Canonical event history remains immutable.
- User content can later be deleted without rewriting event order.
- Logs and event exports avoid leaking message bodies.
- Projection replay can render a deletion tombstone when content no longer exists.

The event, content record, idempotency receipt, and required stream update commit atomically.

P0 deletion is not yet exposed in the UI, but this separation is required now so privacy is not retrofitted after data exists.

# 9. Initial payload schemas

## `workspace/created` v1

```rust
pub struct WorkspaceCreatedV1 {
    pub workspace_id: WorkspaceId,
    pub name: WorkspaceName,
    pub kind: WorkspaceKind,
    pub preferred_language: LanguageCode,
}
```

Constraints:

- P0 kind is `personal`.
- Name is normalized, bounded, and non-empty.
- Language is one of `en`, `ar`, `zh-CN`, or `ru`.

## `project/created` v1

```rust
pub struct ProjectCreatedV1 {
    pub project_id: ProjectId,
    pub workspace_id: WorkspaceId,
    pub name: ProjectName,
    pub storage_kind: ProjectStorageKind,
}
```

P0 storage kind is `adham-owned-isolated`. No raw filesystem path appears in the event.

## `session/created` v1

```rust
pub struct SessionCreatedV1 {
    pub session_id: SessionId,
    pub project_id: ProjectId,
    pub title: Option<SessionTitle>,
}
```

The scope also carries workspace and project identity; the payload repeats the owning project as a meaningful aggregate fact.

## `user/message-submitted` v1

```rust
pub struct MessageSubmittedV1 {
    pub message_id: MessageId,
    pub content_id: ContentId,
    pub content_kind: ContentKind,
    pub size_bytes: u64,
}
```

The event does not contain model routing, memory decisions, or agent state because those capabilities do not exist in the first slice.

# 10. Event metadata

```rust
pub struct EventMetadata {
    pub producer: ProducerId,
    pub producer_version: String,
    pub schema_revision: String,
}
```

Allowed metadata is deliberately small.

Forbidden metadata includes:

- Message text.
- Prompt contents.
- API keys or credentials.
- Raw local file paths.
- Stack traces.
- Entire command payloads.
- Arbitrary environment variables.
- Model context.

New metadata fields require schema review because metadata is persisted and often exported for diagnostics.

# 11. Canonical JSON and integrity

Payloads and metadata use canonical JSON before checksum calculation. Use a documented canonicalization implementation compatible with RFC 8785 rather than relying on incidental object/map iteration order.[[1]](https://www.rfc-editor.org/rfc/rfc8785)

Checksum input uses a versioned binary framing with explicit field lengths:

```
checksum_format_version
previous_checksum
stream_id
stream_sequence
event_id
event_type
event_version
scope
actor
request_id
correlation_id
causation_id
occurred_at
canonical_payload_bytes
canonical_metadata_bytes
```

Compute BLAKE3 over the framed bytes.

Rules:

- First event in a stream has no previous checksum.
- Each later event includes the prior event checksum.
- Replay verifies event checksum and stream chain.
- A checksum failure marks the stream corrupted and blocks projection advancement.
- Repair never silently recomputes a checksum over changed data.
- A diagnostic identifies the stream and sequence without exposing payload content.

The checksum proves accidental or unauthorized storage modification is detectable; it does not authenticate the original writer without a separate keyed signature.

# 12. Event registry

Maintain a checked-in registry:

```json
{
  "registryVersion": 1,
  "events": [
    {
      "type": "workspace/created",
      "version": 1,
      "scope": "workspace",
      "schema": "./workspace/created/v1.json"
    }
  ]
}
```

The registry records:

- Type and version.
- Rust payload type.
- Owning bounded context.
- Allowed stream kind.
- JSON schema path.
- Sensitivity classification.
- First application version.
- Decoder and upcaster availability.
- Projection consumers.

CI fails when:

- A Rust event has no registry entry.
- A registry schema is missing.
- Generated schema differs from the committed snapshot.
- Two entries claim the same type/version.
- A payload contains a forbidden secret or raw-path field by policy rule.

# 14. Decoder and compatibility behavior

Event decoding uses `(event_type, event_version)`.

## Known type and version

Decode, validate, verify scope, and apply.

## Known type, older supported version

Decode the persisted version. An in-memory upcaster may transform it into the current internal representation for projection logic. The stored event remains unchanged.

## Known type, unsupported future version

Stop the affected stream/projection at the previous valid sequence and return `UNSUPPORTED_EVENT_VERSION`. Do not discard, guess, or partially apply it.

## Unknown event type

Stop consumers that require complete semantics. Diagnostic/export consumers may preserve and display the opaque envelope without interpreting its payload.

## Invalid payload

Mark the stream corrupted at the failing sequence. Do not continue replay past it for stateful projections.

# 15. Serialization and schema rules

- Rust payload structs deny unknown fields during strict validation for P0 schemas unless a schema explicitly permits extensions.
- Enums use stable lowercase kebab-case strings.
- Timestamps use UTC RFC 3339 with fixed precision selected in P0-03.
- Integers that may exceed JavaScript’s safe range serialize as strings in IPC, but storage schemas may use SQLite integers where safe.
- Optional and nullable are distinct decisions; do not use `Option` without defining omission versus explicit null.
- Empty strings are invalid for identifiers and names.
- Payload maps with arbitrary keys are forbidden unless canonicalization and limits are explicitly defined.
- Payload size limits are enforced before the transaction begins.

# 16. Observability and privacy

Default structured logs may include:

- Event type and version.
- Stream kind.
- Sequence and global position.
- Request and correlation IDs.
- Duration and public error code.

Default logs exclude:

- Payload JSON.
- Message content.
- Workspace/project/session names.
- Raw paths.
- Content-store values.

Diagnostic export applies the same redaction policy and never treats a local log as automatically safe to share.

# 17. Required tests

## Schema

- Serde round-trip for every payload.
- Generated JSON Schema snapshot.
- Registry uniqueness and completeness.
- Rejection of invalid enum, empty name, oversized value, and unknown required shape.

## Identity and order

- New stream begins at sequence 1.
- Concurrent expected-sequence conflict permits exactly one append.
- Global positions increase.
- UUID newtypes do not interchange accidentally.

## Integrity

- Valid checksum chain passes.
- Payload mutation fails checksum.
- Envelope mutation fails checksum.
- Removed/reordered event breaks the stream chain.
- Different canonical object-key order produces the same canonical payload bytes.

## Compatibility

- Known v1 event decodes.
- Supported old version upcasts in memory without altering stored bytes.
- Future version blocks projection safely.
- Unknown event type is preserved by opaque diagnostics but not applied to state.

## Privacy

- Message body is absent from the event row and logs.
- Missing/deleted content produces a tombstone projection.
- Wrong-scope event append is rejected.
- Metadata rejects forbidden sensitive fields.

# 18. Acceptance gate

P0-02 is ready for implementation when:

- Naming and separate versioning are accepted.
- UUID and timestamp representations are fixed.
- Scope and actor rules are accepted.
- Sensitive-content separation is accepted.
- Checksum framing and algorithm are accepted.
- Initial four payload schemas are reviewed.
- Event registry format is reviewed.
- Unknown/future/corrupt behavior is accepted.
- Tests can be implemented without unresolved semantic choices.

After approval, P0-03 defines the concrete SQLite schema, transactions, idempotency receipts, content storage, projection cursors, migrations, WAL configuration, backup, and recovery.
